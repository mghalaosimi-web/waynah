# WAYNAH SYSTEM LOGIC MASTER STUDY

> وثيقة دراسة مجال ومنطق منتج. لا تتضمن هذه الوثيقة كوداً أو مخطط قاعدة بيانات أو قرار تنفيذ. الحالة المرجعية للمشروع هي 1 أكتوبر 2026، والنطاق الجغرافي التشغيلي الأول: محافظة حجة، مع قابلية التوسع إلى اليمن.

## 1. Executive Summary

WAYNAH منصة اكتشاف جغرافي موثوقة: تساعد الناس على معرفة **ما الموجود، أين يوجد، لمن يتبع، وما الإجراء الممكن فعله الآن**. تبدأ القيمة من الدليل المكاني، لا من التجارة الإلكترونية. لذلك لا يلزم أن يبيع كل نشاط منتجات، ولا أن يقبل طلبات، ولا أن يقدّم توصيلاً.

المجال يتكون من طبقة جغرافية مرجعية، وطبقة أماكن قابلة للاكتشاف، وطبقة أعمال اختيارية تدير نشاطاً أو أكثر، وطبقة عرض/تفاعل تتدرج حسب قدرة كل نشاط. الثقة مصدرها وملاحظاتها وقرار التحقق مستقلّة عن وجود المكان وعن ملكية النشاط وعن جودة الخدمة. هذه الفواصل تمنع تحويل دليل محلي متنوع إلى متجر موحد بصورة مصطنعة.

أهم نتيجة: الوحدة العامة الأولى هي **Place** (شيء يمكن إيجاده أو زيارته أو الإشارة إليه جغرافياً)، وليست Business ولا Product ولا Order. أما الخدمات والمنتجات والمعاملات فهي قدرات اختيارية تتبع عرضاً محدداً أو فرعاً أو مزوداً، بعد إثبات الحاجة التشغيلية لكل فئة.

## 2. What WAYNAH Is

WAYNAH دليل جغرافي وطبقة ثقة وتفاعل محلية لليمن. يعرض الأماكن والأنشطة والخدمات والمزودين وفق الموقع والتصنيف والموثوقية وحالة التوفر، ثم يتيح الإجراء المناسب: اتصال، ملاحة، استفسار، طلب، حجز، أو استقبال خدمة. وهو ليس دليلاً هاتفياً ساكناً، ولا سوقاً إلكترونياً شاملاً، ولا شركة توصيل افتراضياً.

## 3. Problem Definition

المستخدم في حجة قد يعرف حاجته لكنه لا يعرف الاسم الدقيق، الموقع، ساعات العمل، هل النشاط لا يزال قائماً، من المسؤول، أو إن كانت الخدمة تصل إلى منطقته. وفي المقابل قد يملك النشاط وجوداً فعلياً من دون بيانات رقمية موثوقة. يحل WAYNAH فجوة الاكتشاف والثقة والسياق الجغرافي؛ ولا يعد المستخدم تلقائياً بسعر أو مخزون أو تنفيذ أو توصيل ما لم يكن ذلك معلناً ومثبتاً للنشاط المعني.

## 4. System Boundaries

**داخل النظام:** الدليل الجغرافي، البحث والتصفية، الصفحات العامة، بيانات النشاط المعلنة، إثباتات ومطالبات الملكية، ملاحظات المصادر، التصحيح والمراجعة، والتفاعل المشروط الذي يتيحه النشاط.

**خارج النظام حالياً:** ضمان جودة كل خدمة، ضمان توافر المخزون، تحصيل الأموال، تحمل مسؤولية التوصيل، فض النزاعات التجارية، أو التمثيل القانوني للنشاط. يمكن أن تصبح بعض هذه القدرات ضمن WAYNAH مستقبلاً بعقود تشغيلية وقانونية مستقلة.

**ما يستطيع المستخدم فعله:** اكتشاف ومقارنة وحفظ ومشاركة مكان، الحصول على اتجاهات، الاتصال أو التواصل، الإبلاغ عن خطأ، واقتراح مكان. وإذا عرض النشاط قدرة صريحة، قد يستفسر أو يطلب أو يحجز.

**ما لا ينبغي أن يفعله WAYNAH:** اختراع عنوان أو ملكية أو توفر؛ عرض "موثّق" بمعنى أوسع من الدليل؛ تحويل الاستفسار إلى عقد شراء؛ أو فرض تجربة طلب/توصيل على نشاط اكتشاف فقط.

| Product | سلعة/وحدة بيع قابلة للوصف والتسعير والتوفر | وصف، وحدة، سعر/نطاق، توفر | Branch/Business | اختياري؛ قد يقود إلى Order؛ يختلف عن Service |
| User | هوية حساب تستخدم المنصة | هوية اتصال، موافقات، دور | الشخص/النظام | ينشئ حفظاً وتقارير وتفاعلات |
| Business Member | تفويض شخص لإدارة Business | Business، User، دور، حالة | Owner/Manager وفق السياسة | تابع لـBusiness وUser؛ ليس إثبات ملكية قانونية بذاته |
| Inquiry | رسالة لطلب معلومة بلا التزام | موضوع، رسالة، وجهة، حالة | User/النشاط | لا يحجز مخزوناً أو وقتاً |
| Request | طلب تنفيذ أو تقييم قابل للقبول/الرفض | الحاجة، السياق، حالة | User والطرف المستلم | قد يصبح عرض سعر أو Booking أو Order؛ ليس مرادفاً لها |
| Booking | حجز وقت/سعة محددة | الموعد، المدة، المورد، حالة | العميل وProvider/Branch | يتطلب Service قابلة للجدولة |
| Order | التزام بشراء عناصر/سعر/تسليم أو استلام | عناصر، سعر متفق، حالة | العميل والبائع | يتطلب Product أو عرض خدمة قابل للبيع؛ لا ينشأ من الاكتشاف تلقائياً |
| Fulfillment | تنفيذ ما وُعد به | طريقة، مسؤول، تقدم، إثبات | الطرف المنفذ | يتبع Booking أو Order أو Request مقبول |
| Delivery | جزء من fulfillment ينقل شيئاً مادياً | طرف مسؤول، منطقة، موعد، رسوم، إثبات | البائع/طرف ثالث/WAYNAH فقط بعقد | لا يلزم كل Order ولا يصلح للخدمات عن بُعد |
| Review | رأي بعد تجربة مثبتة أو معلنة النوع | تقييم، نص، موضوع، مصدر، حالة | User مع مراجعة | لا يثبت الوجود أو الملكية؛ يعتمد على سياسة أهلية |
| Verification | قرار محدد الادعاء ونطاقه ودليله | نوع الادعاء، دليل، مراجع، صلاحية | Reviewer مخول | يثبت ادعاءً محدداً، لا "كل شيء" |

**الفروق الحاكمة:** Place ≠ Business: قد يكون المكان معلماً أو منشأة بلا صاحب حساب، وقد يملك نشاط واحد عدة أماكن. Business ≠ Branch: الشركة هوية/مظلة، والفرع وحدة تشغيل محلية. Service ≠ Product: الخدمة أداء وسياق زمني، والمنتج سلعة ووحدة كمية. Location هو وصف موضع، لا هوية المكان. Provider قد يكون مستقلاً ولا يحتاج Branch ثابتاً.

## 7. Core User Journeys

1. **اكتشاف فقط:** حاجة → بحث/تصنيف/خريطة → صفحة Place → تقييم الملاءمة والثقة → اتصال أو ملاحة أو حفظ. لا توجد معاملة.
2. **خدمة عند العميل:** حاجة → مزود/Service ونطاقها → استفسار أو Request → قبول وشروط → تنفيذ → تغذية راجعة. العنوان قد يبقى خاصاً حتى قبول الطلب.
3. **خدمة بموعد:** اكتشاف → عرض خدمة مجدول → اختيار وقت متاح → Booking مؤكد → حضور/تنفيذ → إكمال ومراجعة.
4. **سلعة:** اكتشاف → التأكد من التوفر والسعر → Order إن كان البائع يفعّله → استلام ذاتي أو fulfillment/Delivery متفق عليه → إكمال.
5. **تصحيح مجتمعي:** ملاحظة مكان خاطئ/مغلق → بلاغ بمصدر/وقت → مراجعة أو دمج → عرض حالة محدثة مع أثر تدقيقي.

ليست كل أسهم الرحلة إلزامية. "Understand availability" واجب فقط عند ادعاء التوفر؛ و"Fulfillment/Payment/Review" لا تظهر إلا لمسار معاملات مفعّل.

## 8. Discovery Logic

من "أريد شيئاً" إلى نتيجة مناسبة عبر إشارات قرار، لا خوارزمية نهائية: النص وأسماء بديلة؛ التصنيف؛ قرب المستخدم/المنطقة؛ نوع النشاط؛ حالة الفتح أو توفر القدرة إن توافرت؛ الثقة وصلاحية آخر تحديث؛ التقييم المعبّر عن تجربة؛ واكتمال البيانات.

يعرض النظام سبباً مفهوماً للنتيجة مثل: قريب، ضمن التصنيف، مفتوح حسب البيانات المعلنة، موثق في جانب معين، أو بياناته قديمة. لا يجوز للترتيب أن يحول نقص البيانات إلى حكم سلبي مطلق أو أن يخفي نتيجة أساسية لمجرد أنها غير تجارية.

## 9. Geographic Logic

العلاقة المرجعية: Country → Governorate → District → Place → Location. وتبقى الحقيقة الإدارية منفصلة عن عنوان المستخدم وعن منطقة خدمة المزود. قد يكون للـBusiness فروع في مناطق متعددة، وقد تخدم Service عدة Districts بلا موقع استقبال ثابت.

GPS دليل موضع بدرجة دقة، لا عنوان تسليم كامل. الاسم المحلي/المعلم/وصف الوصول قد يكون أهم من عنوان رسمي؛ يحفظ كبيانات وصفية ومصدرها وتاريخها، ولا يترجم إلى حدود إدارية مخترعة. تُعرض المناطق خارج التغطية صراحة، وتُعالج اختلافات التهجئة والأسماء المحلية كبدائل بحث لا كمديريات جديدة.

تعتمد هذه الدراسة أساس GEO-001 إلى GEO-005 الموثق في المشروع ولا تعيد تصميمه.

## 10. Place Logic

Place هو سجل الاكتشاف للواقع المحلي: قد يمثل محلاً، مطعماً، صيدلية، ورشة، مكتب خدمة، معلماً، أو نقطة استقبال. له دورة حياة مستقلة: مرصود، منشور بحذر، نشط، يشتبه بإغلاق/نقل، مغلق، مدمج/مكرر. لا يُحذف تاريخ المكان لمجرد الإغلاق؛ تُحفظ الحالة والزمن والمصدر.

لا يصبح Place، بحد ذاته، Business. يتحول الربط إلى Business عندما يوجد ادعاء قابل للإثبات أن نشاطاً منظماً يدير ذلك الموضع. لا يمنح الادعاء حق تعديل السجل قبل مراجعته، ولا يلغي مساهمات المجتمع أو السجل الجغرافي.

## 11. Business Logic

Business هو الكيان التشغيلي/التجاري. قد يبدأ بلا Place (خدمة متنقلة، شركة ناشئة، عمل عن بعد)، وقد يملك Places متعددة بلا افتراض أنها فروع تشغيلية متكافئة. العلاقة الصحيحة هي: Business يدير Branch واحداً أو أكثر؛ وكل Branch قد يقدم في Place، أو في عدة نقاط، أو بلا موضع ثابت. إن لم تكن هناك بنية فروع حقيقية، لا تُنشأ فروع وهمية لمجرد ربط الأماكن.

**REVIEW REQUIRED — العلاقة الحالية المباشرة بين Place وBusiness.** هي مفيدة كبداية للدليل، لكنها لا تمثل وحدها الفرق بين هوية الشركة والفرع والموضع التشغيلي، ولا تكفي للنشاط المتنقل أو تعدد المواضع. يلزم تثبيت سيناريوهات التشغيل الفعلية قبل تعديلها.

## 12. Branch Logic

الفرع ليس تكراراً لاسم Business؛ إنه موضع أو وحدة تشغيل لها ساعات/مخزون/طاقم/قدرات أو سياسات قد تختلف. يستخدم فقط عند وجود فرق تشغيلي مهم للمستخدم. فرع مغلق مؤقتاً لا يعني أن Business مغلق، وفرع نقل موقعه يحتفظ بأثره التاريخي بدلاً من تبديل إحداثيات سجل قديم بصمت.

## 13. Service Logic

الخدمة وعد بأداء: صيانة، سباكة، كهرباء، برمجة، نقل، تنظيف، استشارة، حجز أو خدمة منزلية. نمط الأداء يحدد المنطق: في مكان ثابت، عند العميل، عن بُعد، أو متنقل؛ فوري أو بموعد؛ بسعر معلن أو نطاق أو عرض سعر.

النموذج المشترك هو: تعريف الخدمة → أهلية/نطاق → توفر → طلب أو موعد عند الحاجة → قبول شروط → تنفيذ → إتمام. لا تفترض سعراً ثابتاً أو وقتاً أو وصولاً جغرافياً. "خدمة متاحة" ادعاء متغير الزمن ويحتاج تاريخ تحديث.

## 14. Product Logic

المنتج سلعة قابلة للبيع، وليس مجرد وصف للنشاط. يختلف البيع بالتجزئة والجملة والعبوات والوزن والوحدات والطلب حسب الطلب؛ وبالتالي قد يكون السعر للوحدة أو الوزن أو حد أدنى أو بعرض سعر. التوفر قد يكون متاحاً أو غير متاح أو غير معروف، ولا يجب أن يقرأ المستخدم "غير معروف" على أنه متوفر.

تحتاج أي تجربة تجارية لاحقة إلى تمييز: مواصفات/بدائل، وحدة وكمية، حالة المنتج، نطاق سعر، وسياسة ضمان/إرجاع إن وجدت. لا يصمم هذا المستند مخططاً لهذه البيانات.

## 15. Request / Booking / Order Logic

| المصطلح | متى يستخدم | ما لا يعنيه |
|---|---|---|
| Inquiry | سؤال عن معلومة أو أهلية أو سعر أو توفر | التزاماً أو حجزاً أو موافقة |
| Request | طلب من المستخدم لتنفيذ/تقييم حاجة وقد يحتاج قبولاً | سعراً أو وقتاً أو تكوين عقد |
| Booking | حجز مورد أو وقت أو سعة محددة ومؤكدة | بيع سلعة أو تسليم تلقائي |
| Order | اتفاق لشراء عناصر/قيمة وشروط واضحة | أن التوصيل أو الدفع تم |

الانتقال من الاكتشاف إلى أي منها يحصل فقط عندما تعلن الجهة المستلمة القدرة وتقبل السياق. الطلب الجزئي لا يكتمل بصمت؛ يظل بحاجة إلى توضيح أو قبول تعديل.

## 16. Fulfillment Logic

Fulfillment هو المرحلة التي تنفذ فيها الجهة ما قبلته، وقد يكون حضوراً، تجهيزاً، خدمة عن بعد، خدمة لدى العميل، أو استلاماً. يجب أن يظل مستقلاً عن Delivery: تنفيذ خدمة استشارة عن بعد لا يتضمن توصيلاً، واستلام العميل لمنتج قد يكون fulfillment بلا Delivery. حالات مفاهيمية: مقبول، مجدول، قيد التنفيذ، مكتمل، فاشل، ملغى، مع سبب وأثر زمني.

## 17. Delivery Logic

النماذج الممكنة: لا توصيل؛ استلام العميل؛ توصيل بواسطة Business؛ طرف ثالث؛ WAYNAH Delivery؛ مجدول؛ أو عند الطلب. صاحب النموذج هو المسؤول عن المنطقة والسعر والمخاطر وإثبات الفشل. لا تنسب WAYNAH لنفسها دور الناقل لمجرد أنها عرضت نشاطاً.

عند غموض العنوان: يطلب تأكيداً وصفياً/نقطة تواصل مع حماية الخصوصية، وقد يتحول إلى نقطة استلام أو يفشل وفق السياسة. عند فشل التسليم: يسجل السبب والحيازة والتكلفة ومن يقرر الإعادة أو الإلغاء؛ لا تعتبره المنصة خطأ العميل أو المندوب تلقائياً.

## 18. Money Logic

منطق المال يفصل السعر الأساسي عن رسوم التوصيل والخصم والعمولة والضريبة إن وجدت والمبلغ النهائي. يثبت السعر المتفق عليه فقط عند مرحلة تقبل ذلك، لا عند نتيجة بحث. الدفع عند الاستلام والدفع الإلكتروني قناتان مختلفتان من حيث المخاطر والإثبات والاسترداد. الإلغاء والاسترداد يتبعان الحالة والجهة وسياسة معلنة؛ لا يطبق نظام استرداد موحد قبل معرفة نماذج التجارة الفعلية.

## 19. Trust & Verification Logic

لا توجد شارة ثقة واحدة شاملة. تُفصل أربعة ادعاءات: (1) وجود Place، (2) صحة بياناته، (3) صلة شخص/Business بالنشاط، (4) جودة تجربة Service أو Product. "Observed" و"Imported" و"Community reported" مصادر أو أدلة؛ "Claimed" ادعاء ملكية؛ "Official" صفة مصدر؛ و"Verified" نتيجة مراجعة محددة النطاق والصلاحية.

المعلومات المتضاربة لا تحل بالكاتب الأخير. تحفظ الملاحظة ومصدرها ووقتها ودرجة ثقتها، ثم يراجع التعارض أو يعرض بحذر. لا يستطيع صاحب النشاط ضبط درجته أو حالة تحققه من الواجهة.

**REVIEW REQUIRED — حالات التحقق الحالية المتعددة للمكان والعمل.** يوجد أساس جيد للتحقق وملكية الأعمال، لكنه يمزج في بعض التسميات بين حالة المكان، ادعاء العمل، والمصدر. قبل توسيع الشارات العامة يجب تعريف معنى كل حالة ودليلها وانتهاء صلاحيتها.

## 20. Data Logic

مصادر البيانات: رسمية، من النشاط، من المستخدم، مستوردة، ملاحظة ميدانية، شريك، مجتمع، أو مولدة من النظام. أولوية المصدر ليست قاعدة مطلقة؛ تحدد لكل نوع ادعاء. مثال: مصدر رسمي أعلى للحدود الإدارية، ومالك موثّق أقوى لساعات عمل فرعه، بينما الملاحظة الحديثة قد تكون أقوى لإبلاغ إغلاق مؤقت.

كل قيمة قابلة للتغير تحتاج تاريخاً ومصدراً وحالة مراجعة. الدمج يربط السجلين المتطابقين ويصون المراجع التاريخية؛ الحذف ليس الوسيلة الافتراضية. التقادم يعيد تقييم الثقة أو يوسم المعلومة، لا يمحو وجود المكان.

تستفيد الدراسة من معمارية Discovery / Observation / Confidence القائمة ولا تقترح إعادة تصميمها. **REVIEW REQUIRED:** احتساب الإجماع الحالي من تطابق الاسم أو الفئة وحدها قد يعطي ثقة زائدة عند تشابه الأنشطة؛ هذا سؤال معايرة بيانات لا تعديل مطلوب الآن.

## 21. Security & Privacy Logic

المبدأ: أقل صلاحية، فصل بين الهوية العامة والبيانات الخاصة، قرار خادمي لكل ملكية، وأثر تدقيقي للقرارات الحساسة. لا يعرض عنوان العميل الدقيق أو رقم الاتصال أو أدلة التحقق أو هوية المبلّغ إلا للجهة المخولة وللغرض اللازم. مشاركة الموقع تكون صريحة ومحددة المدة/الغرض. يمنع انتحال الملكية، إدخال ملاحظات آلية غير موثوقة، إساءة تقييمات المنافسين، وتسريب بيانات الطلبات.

يبقى RBAC وحماية IDOR الحالية أساساً صالحاً، مع ضرورة أن تتسع السياسة مستقبلاً للأفعال على Branch وProvider وطلب لا أن تعتمد على دور User عام فقط.

## 22. Administration Logic

الإدارة تفصل مهام السياسة، إدخال البيانات، فض التعارض، التحقق، وإدارة التصنيفات. كل قرار مؤثر يجب أن يحمل: من اتخذه، لماذا، الدليل/المصدر، التاريخ، والنطاق. لا يكون مشغّل البيانات مراجعاً نهائياً لأدلة أدخلها دون ضابط تعارض مصالح. تحتاج الإدارة طوابير مستقلة للادعاءات، التعارضات، التقادم، الإغلاق/النقل، والإبلاغات الأمنية.

## 23. Edge Cases

- محل مغلق مؤقتاً أو نهائياً، أو انتقل؛ لا يعاد استخدام السجل تلقائياً لمحل آخر.
- اسمين عربيين/إنجليزيين أو لقب محلي لنفس المكان؛ يحتفظ بالبدائل ولا ينشئ تكرارات.
- Business واحد بعدة فروع، أو عدة أنشطة داخل مكان واحد، أو نشاط مشترك لموقع واحد.
- مزود متنقل أو منزلي أو موسمي بلا عنوان استقبال عام.
- بيع جملة وتجزئة مع حد أدنى ووحدات ووزن مختلفة.
- منتج/خدمة غير متاحين رغم أن Place نشط.
- GPS عند مدخل مجمع أو بدقة ضعيفة، وعنوان محلي وصفي فقط.
- إدعاءان متنافسان لملكية Business أو Place، أو مدير سابق ما زال يملك جلسة.
- تغيير اسم Business مع استمرار Place، أو بيع المكان لنشاط جديد.
- طلب مقسّم أو ملغى أو لا يمكن تنفيذه جزئياً؛ وعرض سعر انتهت صلاحيته.
- عدم وجود تغطية أو انقطاع اتصال أو عدم إمكان تسليم آمن.
- تقييم انتقامي، أو تقييم لخدمة لم ينفذها صاحب التقييم.

## 24. Failure Scenarios

| السيناريو | الأثر | الاستجابة المنطقية |
|---|---|---|
| نتيجة تشير إلى مكان مغلق | فقدان ثقة/رحلة فاشلة | وسم التقادم، استقبال بلاغ، عدم حذف التاريخ |
| دمج خاطئ لمكانين متشابهين | فقدان بيانات أو ملكية | قابلية عكس الدمج وأثر مراجعة |
| ادعاء ملكية احتيالي | استيلاء على صفحة | لا تنفذ امتيازات حساسة قبل تحقق مستقل |
| إحداثيات خاطئة | ملاحة/تسليم خاطئ | عرض دقة المصدر وطلب تأكيد عند الأثر العالي |
| معلومة توفر قديمة | طلب غير قابل للتنفيذ | عرض زمن التحديث وعدم ضمان التوفر |
| فشل التوصيل | خسارة/نزاع | تحديد صاحب المسؤولية وسجل محايد للحدث |
| تسريب موقع عميل | ضرر خصوصية | تقليل الإفصاح وربط الوصول بالمرحلة والتفويض |

## 25. Anti-Patterns

- نموذج واحد لكل Place وBusiness وProvider وBranch.
- أنواع نشاط مبرمجة مسبقاً أو حتمية أن كل نشاط يبيع/يوصل.
- تعيين جغرافي زائف أو نسخ الحقيقة الإدارية داخل سجلات متعددة.
- ثقة يتحكم بها المتصل أو مالك النشاط، أو شارة "موثق" بلا نطاق.
- ملكية Business ضمنية لمجرد معرفة رقم الهاتف أو إنشاء حساب.
- اعتبار كل رسالة Order أو كل طلب Booking.
- حذف أو استبدال السجل عند الإغلاق/النقل بدلاً من حفظ التاريخ.
- خلط مصدر الحقيقة مع أحدث تعديل، أو دمج البيانات المتعارضة بلا قرار.
- نشر بيانات الاتصال أو الموقع الدقيق للعميل في صفحة عامة.
- جعل التقييم هو الدليل على الوجود أو الملكية.

## 26. Dependency Graph

```text
Authoritative geography ──> administrative context ──> Place discovery
Data sources/observations ──> identity resolution ──> confidence/conflict handling
Place + verified relationship ──> Business profile
Business (optional) ──> Branch (only when operationally distinct)
Branch or Provider ──> Service / Product offers (optional)
Service offer ──> Inquiry / Request / Booking
Product offer ──> Inquiry / Request / Order
Accepted request / booking / order ──> Fulfillment
Physical fulfillment + declared carrier ──> Delivery
Accepted price + payment method ──> Payment
Completed eligible interaction ──> Review
Evidence + reviewer decision ──> scoped Verification
```

الثقة والبيانات ليستا نهاية السلسلة؛ هما طبقتان عرضيتان تؤثران في كل مرحلة. كذلك يمكن الوصول إلى Place من الخريطة بلا Business، أو إلى Provider بلا Place.

## 27. Domain Relationships

```text
Governorate 1 ── * District 1 ── * Place 1 ── 0..1 Location
Category 1 ── * Place
Business 1 ── * Business Member * ── 1 User
Business 0..1 ── * Branch 0..* ── 0..* Place
Branch or Provider ── 0..* Service / Product
User ── 0..* Inquiry / Request / Booking / Order / Review
Verification ──> one scoped claim about Place, Business, Branch, Provider, or data attribute
Observation/Data Source ──> Place and its attributes; may create conflict, never automatic ownership
```

هذه علاقات مفاهيمية وليست مخطط تنفيذ أو قاعدة بيانات.

## 32. Final Conceptual Architecture

```text
WAYNAH
├── Geography (country, governorates, districts, spatial context)
├── Discovery (search, filters, map, ranking explanations)
├── Places (canonical real-world discoverable entities)
├── Data & Trust (sources, observations, conflicts, scoped verification)
├── Business Identity (businesses, memberships, claims)
├── Operating Presence (branches and providers, when real)
├── Optional Offers (services and products)
├── Optional Interactions (inquiries, requests, bookings, orders)
├── Optional Execution (fulfillment and declared delivery)
├── Optional Money (pricing, payment, cancellation, refund)
├── Users & Feedback (accounts, favorites, eligible reviews)
├── Administration (policy, moderation, audit, operations)
└── Security & Privacy (authorization, consent, protection)
```

الطبقات الاختيارية لا تصبح تبعيات إلزامية لطبقات الاكتشاف. الأمن والخصوصية والبيانات والثقة طبقات عرضية وليست شاشة أخيرة.

## 33. Recommended Study Sequence

1. تثبيت معجم المجال وتعريفات Place/Business/Branch/Provider مع أمثلة حقيقية من حجة.
2. إجراء مقابلات/ملاحظة تشغيلية لعينات من البقالة، الصيدلية، الورشة، المطعم، الخدمة المنزلية، الشركة متعددة الفروع، والمزود المتنقل.
3. رسم رحلات المستخدم لكل عينة وتحديد أقل إجراء ذي قيمة، دون بناء معاملات.
4. تحديد سياسة المصدر والثقة والتقادم والتعارض، ثم تدقيق دلالات حالات التحقق القائمة.
5. حسم سياسة الادعاء والملكية وربط النشاط بالمكان/الفرع.
6. إن تقرر تفاعل تجاري لفئة محددة، دراسة Request/Booking/Order وFulfillment وDelivery والمال لتلك الفئة فقط، مع الاستشاري المناسب.
7. مراجعة النتائج لاتخاذ قرار نطاق المرحلة التنفيذية التالية.
